Desired State và Reconciliation: đọc control loop Kubernetes

Hiểu controller quan sát object, so sánh trạng thái thật với spec rồi thực hiện thay đổi qua API để hội tụ dần.

Kubernetes không chạy một lệnh tạo đủ Pods rồi quên chúng. Controllers liên tục watch objects, tính xem trạng thái hiện tại còn lệch spec ở đâu và ghi các object cần thiết qua API. Đây là cách hiểu hữu ích nhất để đọc lỗi và dự đoán phản ứng của cluster.

Sau bài này, bạn có thể

  • Diễn giải desired state, observed state và reconciliation loop.
  • Nêu controller nào sở hữu từng tầng trong Deployment → ReplicaSet → Pod.
  • Dự đoán controller phản ứng thế nào khi xóa một Pod được quản lý.
  • Phân biệt Pod object bị thay với container restart bên trong cùng Pod.

Controller là control loop

spec / desired state
        |
        v
watch and read API objects
        |
        v
compare desired with observed
        |
        v
create / update / delete related objects
        |
        +------> observe again

Controller thường không sửa trực tiếp container trên node. Nó tạo hoặc cập nhật API objects; controllers khác, scheduler, kubelet và runtime tiếp tục các bước riêng. Mỗi vòng có thể chạy nhiều lần và có retry. Trạng thái có thể dao động do load, failure hoặc external changes mà không có một thời điểm mọi thứ ổn định hoàn toàn.

Ownership: Deployment không trực tiếp sở hữu Pod

Deployment
    | owns
    v
ReplicaSet
    | owns
    +------ Pod A
    +------ Pod B

Deployment controller tạo hoặc cập nhật ReplicaSet để thực hiện rollout. ReplicaSet controller quan sát selector và số replica, rồi tạo hoặc xóa Pods. Pod object lưu ownerReference trỏ tới ReplicaSet. Scheduler chỉ gán Pod chưa có node; kubelet thực thi Pod đã gán trên node.

Vì vậy, khi learner xóa Pod bằng kubectl, họ không “xóa ứng dụng”. Họ xóa một instance object do ReplicaSet quản lý. Nếu Deployment và ReplicaSet còn tồn tại với replicas=2, controller cố tạo Pod thay thế.

Failure experiment: xóa một Pod được quản lý

Chạy make -C labs/kubernetes/01-foundations test hoặc thực hiện theo hai terminal:

# Terminal 1: theo dõi Pods
kubectl get pods -n atlas-foundations -l app.kubernetes.io/name=atlas-demo-api -w

# Terminal 2: kiểm tra hierarchy rồi xóa một Pod
kubectl get deployment,replicaset,pods -n atlas-foundations
kubectl delete pod <pod-name> -n atlas-foundations

Quan sát Pod bị xóa rời danh sách, ReplicaSet tạo Pod mới, Pod mới được scheduler gán node rồi kubelet khởi chạy container. UID mới chứng minh đây là object khác. Deployment availability có thể giảm tạm thời trong lúc replacement khởi động.

Điều desired state không hứa hẹn

Controller chỉ có thể hành động dựa trên các API và quyền truy cập nó có. Nếu không node nào đủ resource, image sai, admission policy từ chối, storage không cấp được hoặc dependency hỏng, loop có thể tiếp tục retry nhưng không hội tụ. “Có Deployment object” không đồng nghĩa có Pod Ready.

Xóa trực tiếp Pod không bền vì parent controller tạo lại. Xóa Deployment là thay đổi khác: cascade policy và owner references có thể xóa các dependent objects. Trước khi xóa, hãy xác định owner bằng kubectl describe pod hoặc đọc metadata.ownerReferences.

Quan sát thay vì restart

kubectl get deployment,replicaset,pods -n atlas-foundations
kubectl describe deployment atlas-demo-api -n atlas-foundations
kubectl describe pod <pod-name> -n atlas-foundations
kubectl get events -n atlas-foundations --sort-by=.metadata.creationTimestamp

So sánh desired/ready/available replicas, xem owner chain và events. Pod Pending thường hướng điều tra sang scheduler/capacity/constraints; container crash hướng sang logs; image pull lỗi hướng sang registry hoặc image-load workflow.

Production Notes

Reconciliation là eventual, không phải transaction xuyên nhiều controller. Một rollout có thể tạo nhiều object và các status cập nhật lệch nhịp. Thiết kế application chịu được instance replacement; externalize durable state, handle SIGTERM, và chỉ dùng retry khi operation an toàn. Hệ thống operator tự viết cần reconcile idempotent để cùng input chạy nhiều lần không gây tác dụng phụ lặp.
