Memory Leak và Resource Leak

GC không cứu được cache vô hạn, goroutine leak, timer/socket/file lifecycle hay reference giữ quá lâu.

1. Mental model

Trong ngôn ngữ GC, “leak” thường là dữ liệu vẫn reachable dù business không cần nữa, hoặc tài nguyên ngoài heap không được đóng. Memory có GC không đồng nghĩa program không thể tăng RAM vô hạn.

Bạn cần suy nghĩ bằng ownership: ai tạo resource, ai chịu trách nhiệm release, điều kiện lifetime kết thúc là gì?

Runtime noteNội dung runtime được viết theo Go 1.27 hiện hành. Các chi tiết implementation có thể thay đổi; language/spec behavior mới là contract ổn định.

3. Hiểu sâu hơn

Cache thiếu eviction, slice giữ backing array lớn, global map registry, goroutine block mãi và HTTP body không close đều có thể tạo symptoms “memory/resource leak”.

Heap profile trả lời object nào đang giữ memory; goroutine profile trả lời goroutine đang mắc ở đâu; OS metrics trả lời file descriptor/socket pressure.

4. Khi đặt vào backend thật

Theo dõi RSS/heap/goroutine/FD cùng request rate và queue/cache cardinality. Một graph memory tăng không đủ để chẩn đoán; correlation với workload và profile mới cho root cause.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Chỉ restart service định kỳ để “fix leak”.
  • Cho cache TTL nhưng không giới hạn cardinality/size.
  • Không close/drain HTTP response body đúng lifecycle.

Điều cần mang sang bài tiếp theo

  • GC chỉ reclaim unreachable heap object.
  • External resources vẫn cần Close/cancel.
  • Ownership + bounded state là antidote tốt nhất cho leak.
