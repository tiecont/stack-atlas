Parsing Request và Validation

Decode JSON có giới hạn, phân biệt syntax error với business validation và tránh payload bất tận.

Một endpoint không nên tin dữ liệu từ client. Validation tốt tách ba việc: decode transport, validate shape, rồi enforce business invariant.

1. Decode có giới hạn

gor.Body = http.MaxBytesReader(w, r.Body, 1<<20)
dec := json.NewDecoder(r.Body)
dec.DisallowUnknownFields()

if err := dec.Decode(&input); err != nil {
    // 400
}

Giới hạn body giúp tránh việc endpoint vô tình nhận payload cực lớn và giữ memory/connection quá lâu.

2. Transport validation khác domain validation

Email thiếu format là validation ở boundary. “User này không được apply job này” là business rule và nên nằm gần domain/service logic.

3. Error response phải ổn định

gotype APIError struct {
    Code    string         `json:"code"`
    Message string         `json:"message"`
    Fields  map[string]string `json:"fields,omitempty"`
}

4. Đừng expose lỗi nội bộ

Database error, stack trace hoặc SQL text không nên trả thẳng cho client. Log nội bộ có correlation ID; response chỉ chứa contract cần thiết.

BoundaryValidation là nơi biến input không đáng tin thành dữ liệu mà core logic có thể tin hơn.

Điểm cần nhớ

  • Giới hạn payload trước khi decode.
  • Tách transport validation khỏi business rules.
  • Error contract phải ổn định và không leak internals.
Bài tập thực hànhViết endpoint POST /users giới hạn body 64 KiB, từ chối field lạ và trả lỗi field-level cho email/name.
