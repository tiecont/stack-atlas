Error Handling trong Go

Errors as values: wrap, inspect, classify và giữ context khi đi qua nhiều tầng backend.

1. Mental model

Go coi error là value bình thường. Điều này tạo code có vẻ nhiều `if err != nil`, nhưng đổi lại đường đi của lỗi rất tường minh: nơi nào có thể fail, nơi đó phải quyết định handle hay propagate.

Một error tốt nên mang đủ context để điều tra mà không phá khả năng phân loại ở tầng trên.

2. Code đầu tiên

Gouser, err := repo.FindByID(ctx, id)
if err != nil {
    return User{}, fmt.Errorf("find user %q: %w", id, err)
}

3. Hiểu sâu hơn

`%w` wrap error để giữ chain. `errors.Is` kiểm tra sentinel/error chain; `errors.As` tìm error theo type. Tránh so sánh string message để quyết định logic.

Phân biệt lỗi domain, lỗi dependency và lỗi transport. HTTP 404 là transport decision; “user not found” có thể là domain/repository signal.

Exampleif errors.Is(err, ErrNotFound) {
    // map to domain/transport behavior
}

4. Khi đặt vào backend thật

Một error đi từ PostgreSQL → repository → service → HTTP handler cần thêm context nhưng không bị log lặp ở mọi tầng. Thường log một lần ở boundary quan sát phù hợp, còn các tầng trong wrap/translate khi cần.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Mất root cause vì dùng `%v` thay `%w` khi muốn wrap.
  • So sánh `err.Error()` bằng string.
  • Log rồi return cùng lỗi ở mọi tầng tạo duplicate noise.
  • Expose raw database/internal error cho client.

Điều cần mang sang bài tiếp theo

  • Error là data + control-flow signal.
  • Wrap để thêm context, inspect bằng `errors.Is/As`.
  • Thiết kế taxonomy lỗi giúp API và observability nhất quán.
