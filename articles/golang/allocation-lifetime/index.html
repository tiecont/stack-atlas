Allocation và Object Lifetime

Allocation rate, retention và vì sao “ít alloc” không đồng nghĩa “ít memory”.

1. Mental model

Memory pressure không chỉ là số lần allocation. Hai workload cùng alloc 1 GB/s nhưng khác live heap/retention có thể tạo GC behavior rất khác. Bạn cần phân biệt allocation rate — tốc độ tạo object — và live heap — object vẫn reachable.

Object trở nên reclaimable khi không còn reachable theo GC, không phải ngay lúc variable ra khỏi một block source code theo nghĩa trực giác.

Runtime noteNội dung runtime được viết theo Go 1.27 hiện hành. Các chi tiết implementation có thể thay đổi; language/spec behavior mới là contract ổn định.

3. Hiểu sâu hơn

Một object nhỏ trỏ tới object graph lớn có thể giữ nhiều memory sống. Slice/map/string có reference đến backing data nên retention bug thường đến từ ownership/lifetime, không chỉ “quên free”.

Go tự quản lý memory, nhưng resource bên ngoài như file descriptors, sockets hay DB rows vẫn cần lifecycle explicit.

Examplevar ms runtime.MemStats
runtime.ReadMemStats(&ms)
fmt.Println(ms.HeapAlloc, ms.HeapObjects)

4. Khi đặt vào backend thật

Cache không giới hạn, queue backlog và per-request buffers được giữ trong pool là ba nguồn memory growth phổ biến. Hãy đo heap in-use, allocation rate và application-level queue/cache size cùng nhau.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Chỉ nhìn RSS và kết luận “GC leak”.
  • Dùng `sync.Pool` như cache lâu dài.
  • Giữ pointer/reference trong global registry mà không eviction.

Điều cần mang sang bài tiếp theo

  • Allocation và retention là hai vấn đề khác nhau.
  • Reachability quyết định GC có thể reclaim object hay chưa.
  • Đo memory cùng domain metrics như cache size/queue depth.
