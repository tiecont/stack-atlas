Network Mental Model cho Backend Engineer

Golang Backend Engineering

Backend code thường bắt đầu bằng http.Get hoặc ListenAndServe, nhưng request thật sự đi qua nhiều tầng. Bài đầu tiên xây một mental model đủ đơn giản để bạn biết lỗi đang nằm ở DNS, TCP, TLS hay HTTP.

1. Endpoint = địa chỉ để nói chuyện

Một service network thường được nhận diện bởi IP + port + protocol. IP giúp packet tới đúng machine/network namespace, còn port giúp kernel chuyển traffic tới đúng socket/process.

goaddr := "10.0.0.12:5432"
conn, err := net.Dial("tcp", addr)
if err != nil {
    log.Fatal(err)
}
defer conn.Close()

Địa chỉ 10.0.0.12:5432 chưa nói đây là PostgreSQL. TCP chỉ nhìn thấy byte stream. Chính PostgreSQL protocol mới quyết định các bytes có nghĩa gì.

Mental modelTCP/UDP vận chuyển bytes hoặc datagrams. HTTP, PostgreSQL, Redis, Kafka, gRPC... là protocol ở tầng ứng dụng đặt ý nghĩa lên dữ liệu đó.

2. Socket không phải connection

Socket là abstraction của hệ điều hành cho network I/O. Một TCP listening socket có thể chấp nhận nhiều TCP connections. Trong Go, net.Listener đại diện cho phía đang lắng nghe, còn net.Conn đại diện cho một connection đã thiết lập.

3. Latency không chỉ là thời gian xử lý code

Một outbound HTTP call có thể tốn thời gian ở DNS lookup, TCP connect, TLS handshake, chờ connection pool, gửi request, chờ server và đọc response. Vì vậy “API chậm” không đồng nghĩa “function Go chậm”.

  • DNS: hostname được resolve ra IP nào?
  • Connect: có tạo TCP connection mới hay reuse connection?
  • TLS: có handshake mới không?
  • Server: time-to-first-byte mất bao lâu?
  • Body: response lớn hay downstream đọc chậm?

4. Điều backend engineer cần nhớ

Khi debug, đừng bắt đầu bằng việc tăng timeout. Hãy hỏi tầng nào đang giữ request. connection refused khác hoàn toàn i/o timeout; TLS certificate error khác HTTP 503.

Một câu hỏi tốt“Request đã tới server chưa?” thường chia bài toán làm đôi: nếu chưa, nhìn DNS/TCP/TLS/load balancer; nếu rồi, nhìn HTTP handler/dependency/application.
