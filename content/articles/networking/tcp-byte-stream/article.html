TCP cho bạn một reliable ordered byte stream. Nó không gửi “message” theo cách application thường tưởng tượng. Đây là khác biệt nhỏ nhưng là nguồn của rất nhiều bug khi tự viết protocol.

1. Một connection được thiết lập trước khi trao đổi dữ liệu

Ở mức khái niệm, client kết nối tới server, kernel hai phía thiết lập trạng thái connection, rồi application mới đọc/ghi. Backend engineer không cần thuộc mọi flag TCP để viết API, nhưng nên hiểu connect là một phase riêng có thể timeout.

2. TCP là stream

Nếu client gọi Write hai lần, server có thể đọc dữ liệu thành một lần, nhiều lần, hoặc kích thước khác tùy buffer và timing. Vì vậy protocol phải có framing.

go// Ví dụ protocol đơn giản: mỗi message kết thúc bằng newline.
writer.WriteString("PING\n")
writer.Flush()

line, err := reader.ReadString('\n')

3. Các cách framing phổ biến

  • Delimiter: newline như nhiều text protocol.
  • Length prefix: gửi độ dài trước payload.
  • Fixed length: mỗi frame có kích thước cố định.
  • Self-describing format: parser biết khi object kết thúc.
Sai lầm phổ biếnĐừng giả định Read(buf) sẽ trả về đầy đủ một message chỉ vì phía bên kia vừa Write(message). Luôn xử lý partial read/write theo contract của API.

4. Close cũng có semantics

Khi peer đóng connection bình thường, Read cuối cùng thường dẫn tới io.EOF. Nhưng network failure, reset, deadline hay process crash có thể tạo lỗi khác. Code production nên phân biệt shutdown bình thường với unexpected failure.
