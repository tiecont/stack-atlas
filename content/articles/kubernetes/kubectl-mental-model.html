kubectl là client gửi HTTP requests tới Kubernetes API server. Nó không phải agent chạy workload và cũng không tự biết cluster đúng là cluster nào: kubeconfig, context, user credentials và flags quyết định request sẽ đi đâu.

Sau bài này, bạn có thể

  • Giải thích cluster, user và context trong kubeconfig.
  • Chọn context rõ ràng trước thao tác có tác động.
  • Phân biệt khai báo bằng apply với lệnh imperative tiện cho thử nghiệm.
  • Dùng lệnh đọc trạng thái trước khi quyết định thay đổi.

Đường đi của một lệnh

kubectl command
      |
      v
load kubeconfig: context -> cluster + user
      |
      v
authenticate / authorize with API server
      |
      v
read or mutate Kubernetes API objects

Kubeconfig có thể chứa nhiều cluster, user và context. Context là tổ hợp tên cluster, user và namespace mặc định. Cờ -n có thể override namespace cho command; --context chọn target cluster rõ ràng. Quyền thực sự vẫn được API server quyết định qua authorization.

Trước khi chạy command, xác nhận target

kubectl config current-context
kubectl config get-contexts
kubectl cluster-info --context kind-stack-atlas
kubectl get namespaces --context kind-stack-atlas

Đối với thao tác ghi, truyền --context kind-stack-atlas khi làm lab nếu context hiện tại chưa được xác nhận. Không dán kubeconfig chứa credentials vào issue, log công khai hay bài lab.

Context không phải guardrail bảo mậtĐổi context nhầm có thể gửi request tới production. RBAC, least privilege, review và policy phía cluster mới là boundary thực thi.

Nhóm lệnh theo câu hỏi

  • get: object nào đang tồn tại, labels/status của chúng là gì?
  • describe: resource events và các condition diễn giải ra sao?
  • get events: component nào vừa báo thay đổi hoặc lỗi?
  • logs / logs --previous: process hiện tại hay lần chạy trước ghi gì?
  • exec: cần kiểm tra từ bên trong container nào, với quyền nào?
  • explain: field này thuộc schema/API version nào?
  • api-resources: cluster đang phục vụ loại resource nào?

Bắt đầu bằng read commands, scope namespace/labels, rồi mở rộng phạm vi nếu evidence chỉ sang control plane hay node.

Apply: mô tả intent có thể review

kubectl apply -f gửi resource configuration tới API để tạo hoặc cập nhật object. File trong Git cho phép review, diff và lặp lại. Các lệnh như kubectl run hữu ích cho thử nghiệm nhanh nhưng thường khó audit hơn khi dùng làm nguồn production.

kubectl apply --context kind-stack-atlas -f labs/kubernetes/01-foundations/manifests/
kubectl get deploy,rs,pods -n atlas-foundations
kubectl describe deployment atlas-demo-api -n atlas-foundations

Apply success chỉ xác nhận object request được chấp nhận. Dùng rollout status, readiness, events và application endpoint để xác nhận kết quả thực tế.

Thử nghiệm khám phá

  1. Chạy kubectl config get-contexts; xác định context, cluster và namespace hiện tại.
  2. Chạy kubectl api-resources, rồi lọc resource namespaced.
  3. Dùng kubectl explain deployment.spec và lần lượt mở selector, template và containers.
  4. Sau lab Foundations, dùng get -o yaml, describe và events để giải thích owner chain.
  5. So sánh kết quả khi truyền --context kind-stack-atlas và khi dùng current context; không chạy lệnh ghi vào context chưa xác nhận.

Production Notes

Automation nên pin context/credentials và dùng service identity giới hạn quyền. Tránh dùng tài khoản cluster-admin cho workflow thường ngày. Audit logs, API errors và request scope giúp xác định ai đã thay đổi resource nào. Không coi output của một lệnh duy nhất là toàn bộ trạng thái hệ thống.
