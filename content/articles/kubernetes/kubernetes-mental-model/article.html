Container hóa giúp đóng gói một tiến trình cùng môi trường chạy. Nó chưa trả lời ai chọn máy để chạy tiến trình, ai thay thế nó khi máy hỏng, ai phân phối traffic khi số bản sao thay đổi, hay làm sao rollout phiên bản mới mà vẫn kiểm soát rủi ro. Kubernetes tồn tại để cung cấp một API và tập control loop cho những bài toán điều phối đó.

Sau bài này, bạn có thể

  • Phân biệt đóng gói ứng dụng bằng container với điều phối workload trên một cụm máy.
  • Nêu những việc Kubernetes hỗ trợ và những việc nó không tự đảm bảo.
  • Nhìn một khai báo replica như mục tiêu cần hội tụ, không phải lệnh chạy đúng một lần.
  • Nhận biết ranh giới giữa Kubernetes API và implementation của cluster.

Bài toán trước khi có control plane

Giả sử một API chạy trong container. Nếu chỉ có một máy, người vận hành có thể khởi chạy container bằng tay. Khi máy dừng, cần chọn máy khác, kéo image, chạy tiến trình, cập nhật địa chỉ mà client dùng, rồi kiểm tra readiness. Khi cần deploy phiên bản mới, cần phối hợp số replica cũ và mới để tránh mất capacity.

Những bước này dễ bỏ sót khi số workload, node và nhóm vận hành tăng lên. Container chuẩn hóa gói chạy; một cluster orchestrator nhận mô tả workload và điều phối nhiều thành phần để đạt trạng thái mong muốn.

Image + config
      |
      v
Placement on a node -> run -> observe health
      |                    |
      +--- replace / scale -+
      |
      +--- publish stable discovery endpoint

Sơ đồ là mental model, không phải thứ tự đồng bộ của một request. Trong Kubernetes, API server, controllers, scheduler, kubelet và networking components phối hợp qua API và trạng thái lưu trữ.

Kubernetes cung cấp gì?

Kubernetes cung cấp API objects để khai báo workload và policies; control plane theo dõi objects; scheduler gán Pod chưa có node phù hợp; controllers điều chỉnh tài nguyên liên quan; kubelet trên node làm việc với container runtime để chạy Pod. Các API khác biểu diễn Service discovery, volume, rollout và autoscaling.

Nhờ cách chia này, người khai báo có thể yêu cầu một Deployment duy trì ba replica. Nếu một Pod bị xóa, controller nhìn thấy chênh lệch rồi tạo object thay thế. API server cũng cho phép nhiều công cụ cùng đọc và cập nhật trạng thái theo một giao thức.

Điểm cần giữKubernetes không chạy một script deploy duy nhất. Bạn lưu intent vào API; nhiều control loop quan sát và hội tụ từng phần của hệ thống.

Kubernetes không làm thay ứng dụng

Kubernetes không chứng minh business logic đúng, không biến database đơn lẻ thành hệ thống HA, không tự hiểu request nào có thể retry an toàn, và không đảm bảo một process có thể nhận SIGTERM rồi drain request đúng cách. Những điều đó cần thiết kế trong ứng dụng, dữ liệu và quy trình vận hành.

Một Service là API abstraction cho một tập endpoint; dataplane có thể được hiện thực bởi kube-proxy hoặc thành phần mạng khác. NetworkPolicy chỉ có hiệu lực khi network implementation hỗ trợ enforcement. LoadBalancer, storage, DNS và node provisioning còn phụ thuộc cluster add-ons hoặc provider. Tách contract khỏi implementation giúp tránh hứa hẹn quá mức.

  • Kubernetes API contract: object fields, ownership, trạng thái và semantics được API mô tả.
  • Cluster implementation: CNI, CSI, proxy/dataplane, controller và runtime đang chạy.
  • Provider behavior: load balancer, disk, IAM hoặc node lifecycle do nền tảng cụ thể tích hợp.

Declarative intent là bước chuyển quan trọng

Thay vì yêu cầu “chạy container này một lần”, bạn mô tả trạng thái mong muốn: image nào, bao nhiêu replica, labels và chính sách rollout. Kubernetes lưu object đó và liên tục so sánh với trạng thái quan sát được.

Desired state in API
        |
        v
controllers observe -> compare -> take action
        ^                         |
        +---- report new state ----+

Hội tụ có thể chậm hoặc không hoàn thành nếu cluster thiếu CPU, image không tồn tại, volume lỗi hoặc admission từ chối object. “Đã apply thành công” chỉ nói API server nhận object, không phải application đã phục vụ traffic.

Thử nghiệm tư duy: phân loại trách nhiệm

Chọn một API có database và worker. Với mỗi yêu cầu dưới đây, đánh dấu phần nào thuộc Kubernetes API/control loop, phần nào thuộc ứng dụng, và phần nào phụ thuộc cluster/provider:

  1. Giữ hai bản sao API và thay Pod đã mất.
  2. Không gửi traffic vào bản sao chưa sẵn sàng.
  3. Đảm bảo một payment không bị ghi hai lần khi client retry.
  4. Cấp một external load balancer có địa chỉ công khai.
  5. Khôi phục database từ backup sau khi dữ liệu bị xóa.

Gợi ý: Kubernetes có object/controller liên quan đến một số mục, nhưng sự hiện diện của object không đồng nghĩa hệ thống đã đạt mục tiêu end-to-end.

Production Notes

Ở production, control plane availability, node capacity, admission policies, image distribution, observability và backup đều là một phần của vận hành. Managed Kubernetes thường quản lý một phần control plane và node lifecycle; nó không tự đặt resource requests hợp lý hay thay thế trách nhiệm application team. Hãy hỏi rõ ai sở hữu từng failure boundary trước khi giao workload cho cluster.
