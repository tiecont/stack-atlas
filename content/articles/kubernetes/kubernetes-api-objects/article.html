Kubernetes object là một bản ghi bền vững trong API biểu diễn một phần trạng thái cluster. Manifest không phải shell script: nó mô tả object và intent; API server cùng controllers diễn giải rồi cập nhật trạng thái theo thời gian.

Sau bài này, bạn có thể

  • Đọc bốn trường gốc apiVersion, kind, metadata và spec.
  • Phân biệt spec do client khai báo với status do hệ thống quan sát/cập nhật.
  • Giải thích UID, resourceVersion và generation ở mức dùng an toàn.
  • Dùng kubectl explain và API output để kiểm tra schema thực tế.

Hình dạng của một object

apiVersion: apps/v1
kind: Deployment
metadata:
  name: atlas-demo-api
  namespace: atlas-foundations
  labels:
    app.kubernetes.io/name: atlas-demo-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: atlas-demo-api
  template:
    metadata:
      labels:
        app.kubernetes.io/name: atlas-demo-api
    spec:
      containers:
        - name: api
          image: atlas-demo-api:dev
  • apiVersion chọn API group/version diễn giải object; kind chọn loại resource.
  • metadata chứa name, namespace, labels, annotations và server-generated identity fields.
  • spec diễn tả trạng thái mong muốn theo schema riêng của từng kind.
  • status là trạng thái quan sát được, thường do controller hoặc component hệ thống cập nhật.

Mọi object không có cùng shape chi tiết. Dùng API reference hoặc kubectl explain deployment.spec thay vì đoán field.

Identity và version fields

metadata.uid nhận diện một object cụ thể xuyên suốt vòng đời của nó; xóa rồi tạo lại cùng namespace/name sẽ tạo UID khác. metadata.resourceVersion là token opaque để API hỗ trợ watch và phát hiện cập nhật cũ; không parse nó như timestamp hay số thứ tự toàn cục.

metadata.generation biểu diễn phiên bản mong muốn của object theo semantics của resource. Controller thường báo generation đã quan sát trong status khi reconcile. Không phải mọi status update đều thay đổi generation. Hãy xem nó như tín hiệu API, không tự tăng hoặc dùng làm sequence number nghiệp vụ.

Không copy server fields vào source manifestKhông khai báo UID hoặc resourceVersion cố định trong file Git. Server tạo hoặc quản lý chúng; giá trị từ một cluster không phải cấu hình portable.

Lab: nhìn object qua API

Chạy lab foundations trước để tạo Deployment. Sau đó so sánh object mong muốn và Pod được controller tạo:

kubectl get deployment atlas-demo-api -n atlas-foundations -o yaml
kubectl get pods -n atlas-foundations -l app.kubernetes.io/name=atlas-demo-api -o yaml
kubectl explain deployment.spec
kubectl explain pod.spec.containers.resources
kubectl api-resources --api-group=apps

Trong output, tìm spec.replicas, status.availableReplicas, UID, resourceVersion, generation và ownerReferences. API server có thể thêm defaults nên object trả về thường nhiều field hơn manifest nguồn.

Failure và cách đọc

Nếu kubectl apply báo unknown field hoặc sai apiVersion, request chưa tạo object thành công. Nếu API server chấp nhận object nhưng status không đạt mong muốn, đó là giai đoạn reconcile/schedule/runtime tiếp theo; xem kubectl get, describe và events để tìm component đang chờ hoặc từ chối.

Server-side dry-run kiểm tra request qua API server mà không lưu thay đổi:

kubectl apply --server-side --dry-run=server -f manifests/10-deployment.yaml

Dry-run vẫn cần quyền authorization tương ứng và không kiểm chứng rằng image chạy được hoặc ứng dụng khỏe.

Production Notes

Schema có thể khác theo API version và CRD được cài trong cluster. Hãy pin API versions trong source, kiểm tra deprecation trước khi nâng cluster, và dùng server-side validation trong CI. Tránh để hai field managers cùng ghi một field mà không có ownership rõ ràng.
