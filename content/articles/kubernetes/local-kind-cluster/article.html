kind (Kubernetes IN Docker) khởi chạy Kubernetes nodes dưới dạng containers. Nó tạo một nơi rẻ và có thể xóa để học API/control loops, nhưng node container không tương đương máy production và cluster mặc định không tự cung cấp cloud load balancer hay policy-enforcing CNI.

Sau bài này, bạn có thể

  • Tạo, kiểm tra và xóa cluster riêng có tên bằng kind.
  • Biết các prerequisite là Docker, kind và kubectl.
  • Xác nhận context và version trước khi chạy labs.
  • Phân biệt tính lặp lại của lab với production equivalence.

Vì sao chọn kind?

kind dùng container runtime host để chạy các node Kubernetes và cung cấp kubeconfig context. Cluster có thể tạo/xóa trong vài phút, hoạt động tốt cho CI, và có thể ghim node image digest để lần chạy sau dùng cùng bản build. Minikube là lựa chọn khác nhưng repo này chuẩn hóa CI trên kind để labs có một đường chạy duy nhất.

kind không thay thế managed Kubernetes: networking, storage, external load balancer, cloud IAM và node autoscaling trong provider có thể khác hoặc vắng mặt.

Version baseline được pin

Repo sử dụng kind v0.33.0, kubectl v1.37.0 và node image kindest/node:v1.37.0 với digest phát hành tương ứng. Digest giúp tag không âm thầm trỏ sang image khác. Version matrix ghi baseline và các minor dự kiến tương thích; CI hiện test baseline 1.37.

cd labs/kubernetes/00-cluster
make doctor
make cluster-up
make cluster-info

Cluster config tạo một control-plane node và hai worker để nhìn được placement. Điều này cần nhiều CPU/RAM hơn cluster đơn node; giảm số worker khi máy giới hạn tài nguyên chỉ làm thay đổi lab setup, không thay đổi API semantics.

Xác nhận cluster trước khi học

kubectl config current-context
kubectl cluster-info --context kind-stack-atlas
kubectl get nodes -o wide
kubectl version

Đợi node Ready trước khi apply workload. Nếu kubeconfig chứa nhiều cluster, dùng context được chỉ định trong lệnh. Khi hoàn tất lab, make cluster-down xóa đúng cluster có tên stack-atlas.

Nếu cluster không lên

  • Kiểm tra Docker daemon đang chạy và user có quyền truy cập socket.
  • Dùng docker info để phân biệt lỗi Docker với lỗi download node image.
  • Kiểm tra dung lượng đĩa, RAM và container còn sót bằng kind get clusters.
  • Xem context: kind dùng kind-stack-atlas, không bắt buộc là context mặc định kind-kind.

Đừng xóa mọi Docker container để “reset”. Xóa cluster có tên sau khi xác định nó là cluster của lab.

Production Notes

Cluster local không test high availability control plane, cloud controllers, production CNI/CSI, IAM integration hay failure domain thật. Dùng kind cho API validation, controller behavior cơ bản và reproducible smoke tests. Với provider behavior, cần test riêng trên môi trường đại diện và ghi rõ implementation nào đang chạy.
