Một Kubernetes cluster không phải một daemon duy nhất. Nó là một tập component cùng trao đổi qua Kubernetes API: control plane quản lý trạng thái và quyết định placement; node components thực thi Pod trên máy được chọn.

Sau bài này, bạn có thể

  • Vẽ luồng cơ bản giữa kubectl, API server, etcd, controllers, scheduler, kubelet và runtime.
  • Giải thích thành phần nào quan sát object và thành phần nào chạy container.
  • Phân biệt Kubernetes API contract với cluster-specific implementation.

Bản đồ thành phần

                         CONTROL PLANE
kubectl / API client
        |
        v
  kube-apiserver <------> etcd (persisted cluster state)
     ^       ^
     |       |
controllers  kube-scheduler
     |       |
     +--- create/update objects; bind unscheduled Pods
             |
             v
          NODE
       kubelet watches assigned Pods
             |
       Container Runtime (CRI)
             |
       containers in a Pod

Đây là sơ đồ trách nhiệm logic, không phải topology bắt buộc. Development cluster có thể đặt control plane trên một node/container; production control plane thường phân tán để tăng khả năng chịu lỗi. Kubernetes cho phép component placement và network implementation khác nhau.

Control plane: lưu, quan sát và quyết định

API server

kube-apiserver cung cấp HTTP API và là điểm vào chính cho kubectl, controllers và clients. Request đi qua authentication, authorization và admission trước khi được chấp nhận. API server xác thực object, lưu trạng thái và phát thay đổi cho các client đang watch.

etcd

etcd là backing store key-value nhất quán cho dữ liệu API của cluster. Người dùng workload thường thao tác qua API server thay vì truy cập etcd trực tiếp. Với cluster tự quản lý, backup và restore etcd là trách nhiệm vận hành trọng yếu.

Controllers và scheduler

kube-controller-manager chạy nhiều controller control loop. Một controller có thể tạo hoặc cập nhật object khác qua API; nó không nhất thiết thực thi container. Scheduler theo dõi Pod chưa được gán node, đánh giá resource requests và các constraint rồi ghi quyết định binding. Scheduler không kéo image hay khởi chạy process.

Node: thực thi Pod

Kubelet trên node nhận PodSpec đã được gán và làm việc với container runtime qua CRI để bảo đảm container theo mô tả được chạy. Runtime như containerd hoặc CRI-O chịu trách nhiệm lifecycle container ở tầng node. Kubelet không quản lý các container được khởi chạy ngoài Kubernetes.

Network plugin cung cấp Pod networking; plugin hoặc proxy implementation có thể hiện thực một phần Service behavior. Storage plugin nối volume APIs với hệ thống lưu trữ. Đây là điểm tích hợp, không phải cùng một binary bắt buộc trong mọi cluster.

Trace một Deployment

  1. Client gửi Deployment qua API server; API server kiểm tra request và lưu object.
  2. Deployment controller nhận thay đổi và tạo ReplicaSet object.
  3. ReplicaSet controller tạo Pod objects theo template.
  4. Scheduler chọn node cho mỗi Pod chưa được gán.
  5. Kubelet trên node làm việc với runtime để tạo container.
  6. Status và events được cập nhật; client đọc lại qua API server.

Các bước diễn ra bất đồng bộ. kubectl apply trả về trước khi mọi Pod đã Ready.

Quan sát local cluster

kubectl get nodes -o wide
kubectl get --raw=/readyz?verbose
kubectl get pods -A -o wide
kubectl get events -A --sort-by=.metadata.creationTimestamp

Trong kind, control plane components thường chạy dưới dạng static Pods ở namespace kube-system. Managed cluster có thể không cho bạn xem hoặc quản lý trực tiếp các Pod đó.

Production Notes

Đừng suy ra topology, high availability hay Service dataplane chỉ từ API. Hãy xác minh cách provider triển khai API server/etcd, CNI, CSI, proxying, DNS và cloud controllers. Khi điều tra outage, xác định lỗi ở API/control plane, scheduler, node runtime, network/storage integration hay chính application trước khi thử restart.
