1. Mental model

Escape analysis trả lời câu hỏi: compiler có thể chứng minh storage chỉ cần sống trong scope/frame an toàn hay không? Nếu không, value có thể phải escape sang heap.

Đây là analysis tĩnh và thay đổi khi compiler cải tiến; output diagnostic là công cụ học/điều tra, không phải API stability contract.

Runtime noteNội dung runtime được viết theo Go 1.27 hiện hành. Các chi tiết implementation có thể thay đổi; language/spec behavior mới là contract ổn định.

2. Code đầu tiên

Gofunc value() User {
    return User{Name: "A"}
}

func pointer() *User {
    u := User{Name: "B"}
    return &u
}

3. Hiểu sâu hơn

Capture bởi closure, lưu pointer vào object sống lâu hơn, conversion/interface boxing trong một số context, hoặc trả pointer có thể ảnh hưởng escape. Nhưng optimizer có thể làm kết quả khác trực giác đơn giản.

Dùng `-gcflags=-m` để xem lý do. Sau đó xác nhận bằng benchmark `-benchmem` vì “escape” không tự động nói cho bạn mức ảnh hưởng production.

Examplego test -run=^$ -bench=. -benchmem ./internal/hotpath
go test -gcflags="-m=2" ./internal/hotpath

4. Khi đặt vào backend thật

Escape analysis hữu ích khi tối ưu serializer, parser, hot loop, pool object hoặc middleware chạy trên mọi request. Nó ít quan trọng hơn correctness và tail latency từ dependency ở hầu hết endpoint bình thường.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Refactor code khó đọc chỉ để làm một value “does not escape”.
  • Tin vào blog cũ về compiler behavior mà không kiểm tra toolchain hiện tại.
  • Đếm allocation mà không đo bytes/op, CPU và end-to-end latency.

Điều cần mang sang bài tiếp theo

  • Escape analysis giải thích allocation, không thay thế benchmark.
  • Compiler internals thay đổi; kiểm tra phiên bản đang dùng.
  • Optimize hot path đã được profile.
