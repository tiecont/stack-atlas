1. Mental model

Map cần hash key và tìm vị trí lưu value trong hash table implementation. Exact bucket/layout có thể thay đổi giữa các Go release, nên hãy học invariants: key phải comparable, lookup expected-fast, iteration order không phải contract, mutation concurrent cần synchronization.

Performance của map phụ thuộc cả key type, size, hashing cost và memory locality.

Runtime noteNội dung runtime được viết theo Go 1.27 hiện hành. Các chi tiết implementation có thể thay đổi; language/spec behavior mới là contract ổn định.

2. Code đầu tiên

Gotype Key struct {
    TenantID uint64
    UserID   uint64
}

cache := make(map[Key]User)
cache[Key{1, 42}] = user

3. Hiểu sâu hơn

Composite comparable struct thường là key tốt hơn việc nối string nếu domain phù hợp, vì tránh format/parse và giữ type safety. Nhưng đừng micro-optimize nếu profile không cho thấy map/key hashing nóng.

Deleting entry làm key/value không còn reachable qua map, nhưng runtime memory management và table capacity không nhất thiết lập tức trả memory về OS.

Exampledelete(cache, key)
// removes logical entry; do not assume immediate RSS drop

4. Khi đặt vào backend thật

In-memory caches, dedupe tables và routing metadata thường dùng map. Nếu cardinality không bounded, vấn đề lớn nhất không phải lookup speed mà là memory growth và eviction policy.

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Tin vào một bài blog mô tả bucket internals cũ như contract vĩnh viễn.
  • Map key là string format phức tạp chỉ vì tiện.
  • Cache map không giới hạn trong service lâu sống.

Điều cần mang sang bài tiếp theo

  • Học semantics ổn định trước implementation detail.
  • Key design ảnh hưởng correctness và cost.
  • Map production cần ownership + lifecycle + cardinality control.
