1. Mental model

Package là đơn vị namespace/compilation; module là tập package được version bằng `go.mod`; workspace (`go.work`) giúp phát triển nhiều module local cùng lúc.

Cấu trúc project Go tốt không cần một “chuẩn folder framework”. Hãy tổ chức theo responsibility/domain và giữ dependency direction dễ hiểu.

3. Hiểu sâu hơn

Import path đi qua module path + package subdirectory. `internal/` có semantics đặc biệt: code bên ngoài parent tree không được import package bên trong. Đây là công cụ tốt để tạo boundary compile-time.

`cmd/` là convention phổ biến cho nhiều executable, không phải keyword. `go work` hữu ích khi bạn đang thay đổi đồng thời nhiều module local.

Exampleshop/

  internal/order/
  internal/user/
  internal/platform/postgres/
  go.mod

4. Khi đặt vào backend thật

Với backend lớn, tránh package tên chung chung như `utils`, `helpers`, `common` phình to. Package nên có cohesion. Domain package không nên import transport framework nếu muốn giữ business logic độc lập.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Circular imports vì boundary package không rõ.
  • Một package `utils` trở thành nơi chứa mọi thứ.
  • Tách quá nhiều module quá sớm và tự tăng chi phí versioning.

Điều cần mang sang bài tiếp theo

  • Package boundary quan trọng hơn “folder đẹp”.
  • Module giải quyết version/dependency, không phải mọi folder đều cần module.
  • `internal` là boundary thực sự được toolchain enforce.
