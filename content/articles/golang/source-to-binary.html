1. Mental model

Khi chạy `go build`, toolchain phân tích module/package graph, compile các package cần thiết và link thành executable. Go cache build result để những package không đổi không phải làm lại toàn bộ công việc.

Điều cần giữ trong đầu: source-level semantics thuộc language spec; cách compiler optimize, inline hoặc bố trí binary là implementation detail có thể thay đổi theo release.

Runtime noteNội dung runtime được viết theo Go 1.27 hiện hành. Các chi tiết implementation có thể thay đổi; language/spec behavior mới là contract ổn định.

2. Code đầu tiên

Gogo build -o bin/api ./cmd/api
go version -m bin/api
go env GOOS GOARCH

3. Hiểu sâu hơn

Cross compilation cho nhiều target thường đơn giản bằng `GOOS`/`GOARCH` khi dependency cho phép. Linker gom code cần thiết và runtime vào binary; cgo có thể làm deployment/cross-build phức tạp hơn.

Build tags cho phép chọn source theo platform/feature, nhưng dùng quá nhiều sẽ làm matrix test khó kiểm soát.

ExampleCGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o app ./cmd/api

4. Khi đặt vào backend thật

Trong CI/CD, bạn có thể build một artifact bất biến, scan/test nó rồi promote qua environment. Multi-stage Docker build là natural fit: toolchain ở builder image, runtime image giữ binary + certificate/timezone data nếu cần.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Cho rằng binary luôn “fully static” bất kể cgo/system dependency.
  • Embed build-time secret vào binary.
  • Dựa vào compiler optimization cụ thể như contract.

Điều cần mang sang bài tiếp theo

  • Toolchain là pipeline compile/link + cache, không phải magic.
  • Runtime đi cùng executable theo toolchain chuẩn.
  • Implementation detail có thể đổi giữa release; behavior spec mới là contract.
