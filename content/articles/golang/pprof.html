1. Mental model

Profiling không phải bước cuối khi hệ thống cháy; nó là công cụ để biến cảm giác “chậm/tốn RAM” thành evidence. Go runtime xuất nhiều profile mà `go tool pprof` có thể phân tích.

CPU profile trả lời “CPU chạy ở đâu”; heap trả lời memory đang được giữ/sample; allocs tập trung lịch sử allocation; goroutine/mutex/block giúp concurrency diagnosis.

Runtime noteNội dung runtime được viết theo Go 1.27 hiện hành. Các chi tiết implementation có thể thay đổi; language/spec behavior mới là contract ổn định.

3. Hiểu sâu hơn

Top list hữu ích nhưng flame graph/call graph giúp nhìn call stack. So sánh profile trước/sau thay đổi tốt hơn nhìn một snapshot cô lập.

Profiling có overhead; endpoint pprof có thông tin nhạy cảm về process. Đừng expose công khai ra Internet.

Examplego test -bench=. -cpuprofile cpu.out -memprofile mem.out ./...
go tool pprof cpu.out

4. Khi đặt vào backend thật

CPU cao → CPU profile. RSS/heap tăng → heap + allocs. Request tail latency nhưng CPU thấp → trace/block/mutex/network metrics có thể phù hợp hơn. Chọn tool theo hypothesis.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Optimize function top CPU nhưng thực ra workload benchmark khác production.
  • Expose `/debug/pprof` public.
  • Đọc heap profile như exact census thay vì sampling/tool semantics.

Điều cần mang sang bài tiếp theo

  • Profile theo câu hỏi cụ thể.
  • Dùng production-like workload và so sánh before/after.
  • pprof là evidence, không tự đưa ra design decision.
