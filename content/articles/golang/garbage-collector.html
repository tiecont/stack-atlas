1. Mental model

Toolchain Go chuẩn có garbage collector tracing: runtime tìm object reachable từ roots, đánh dấu object sống và tái sử dụng/reclaim memory không còn reachable. GC giúp developer không manual free memory, nhưng CPU và memory trade-off vẫn tồn tại.

Go GC implementation tiếp tục tiến hóa; hãy xem GC Guide hiện hành khi tuning, không dựa vào một con số pause/algorithm từ bài viết cũ.

Runtime noteNội dung runtime được viết theo Go 1.27 hiện hành. Các chi tiết implementation có thể thay đổi; language/spec behavior mới là contract ổn định.

2. Code đầu tiên

GoGODEBUG=gctrace=1 ./app
# observe GC cycles; do not tune from one sample

3. Hiểu sâu hơn

Hai signal quan trọng là live heap và allocation rate. `GOGC` ảnh hưởng mục tiêu growth của heap giữa cycle; soft memory limit (`GOMEMLIMIT`/runtime API) giúp runtime cân bằng dưới budget memory. Tuning có trade-off CPU ↔ memory.

GC không thể reclaim object vẫn reachable, nên “memory leak” trong Go thường là retention bug hoặc resource leak chứ không phải thiếu `free`.

Exampleimport "runtime/debug"

old := debug.SetMemoryLimit(2 << 30) // example: 2 GiB soft limit
_ = old

4. Khi đặt vào backend thật

Trong container, memory limit thực tế rất quan trọng. Đặt budget cần chừa non-heap memory, stacks, binary mappings và overhead khác; đừng đặt runtime soft limit bằng đúng pod hard limit rồi mong không OOM.

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Tăng GOGC để giảm CPU mà không quan sát memory headroom.
  • Giảm GOGC để giảm memory rồi làm CPU GC tăng mạnh.
  • Nhìn một GC pause rồi kết luận toàn bộ latency đến từ GC.

Điều cần mang sang bài tiếp theo

  • GC cost phụ thuộc live heap và allocation behavior.
  • Tuning là CPU-memory trade-off, phải đo dưới workload thật.
  • Reachability bugs không được GC “tự hiểu” là không cần nữa.
