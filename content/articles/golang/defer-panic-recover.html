1. Mental model

`defer` đăng ký một function call chạy khi function hiện tại kết thúc. Đây là cách Go làm cleanup gần nơi acquire resource: mở file rồi defer Close, lock rồi defer Unlock khi scope phù hợp.

`panic` phá control flow bình thường và unwind stack; `recover` chỉ có ý nghĩa trong deferred function của cùng goroutine. Đây là cơ chế cho tình huống bất thường, không phải replacement cho error.

2. Code đầu tiên

Gof, err := os.Open(name)
if err != nil {
    return err
}
defer f.Close()

// use f
return nil

3. Hiểu sâu hơn

Arguments của deferred call được evaluate tại lúc `defer` được thực thi. Deferred calls chạy theo thứ tự LIFO khi function return/panic.

Trong server, framework hoặc boundary có thể recover panic để process không chết vì một request. Nhưng recover không làm bug biến mất; bạn vẫn cần log/trace và trả lỗi phù hợp.

Examplefunc withTx(ctx context.Context, db *sql.DB) (err error) {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil { return err }
    defer tx.Rollback() // no-op after Commit
    // ...
    return tx.Commit()
}

4. Khi đặt vào backend thật

`defer` cực hữu ích với transaction rollback, mutex unlock, trace span end, file/socket cleanup. Tuy vậy trong loop rất lớn, defer đến cuối function có thể giữ resource lâu hơn bạn tưởng; hãy tạo inner function nếu cần lifecycle theo từng iteration.

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Dùng panic cho validation/user input.
  • Recover rồi bỏ qua panic, che bug production.
  • Defer `Close` trong loop dài và giữ hàng nghìn resource đến cuối function.

Điều cần mang sang bài tiếp theo

  • `defer` làm lifecycle resource gần nhau và dễ audit.
  • Panic dành cho trạng thái bất thường/bug, không phải business error.
  • Recover nên sống ở boundary có chủ đích.
