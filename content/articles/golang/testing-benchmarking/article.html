1. Mental model

Go tích hợp testing vào toolchain: file `_test.go`, package `testing`, benchmark và fuzzing. Điều đáng học không phải chỉ cú pháp assertion, mà là cách thiết kế code có dependency nhỏ để test không cần boot cả application.

Table-driven tests là pattern phổ biến vì Go khuyến khích data + loop thay vì DSL test phức tạp.

2. Code đầu tiên

Gofunc TestNormalize(t *testing.T) {
    tests := []struct{
        in, want string
    }{{" Go ", "go"}, {"API", "api"}}

    for _, tt := range tests {
        if got := Normalize(tt.in); got != tt.want {
            t.Fatalf("got %q want %q", got, tt.want)
        }
    }
}

3. Hiểu sâu hơn

Benchmark dùng `go test -bench=.` và nên tránh đo setup không liên quan. Với allocation, `-benchmem` cho bạn thêm signal. Race detector và fuzzing mở rộng feedback loop cho concurrency/input edge cases.

Không phải test nào cũng cần mock. Fake/in-memory implementation nhỏ thường dễ hiểu hơn framework mock nặng.

Examplego test ./...
go test -race ./...
go test -bench=. -benchmem ./...

4. Khi đặt vào backend thật

Backend nên có nhiều tầng test: unit cho logic; integration cho PostgreSQL/Redis contract; HTTP test bằng `httptest`; benchmark cho hot path đã chứng minh cần tối ưu. Test theo risk, không theo mục tiêu coverage 100%.

Câu hỏi nên tự hỏiKhi concept này đi qua HTTP, database, cache hoặc worker, ownership nằm ở đâu, lifecycle kết thúc khi nào, và failure được biểu diễn ra sao?

5. Sai lầm thường gặp & điều cần nhớ

Sai lầm thường gặp

  • Benchmark micro-code nhưng bỏ qua network/DB bottleneck thật.
  • Test implementation detail khiến refactor nhỏ cũng vỡ hàng loạt test.
  • Mock mọi dependency và cuối cùng test chỉ chứng minh mock hoạt động.

Điều cần mang sang bài tiếp theo

  • Testing là feedback loop, không phải ceremony.
  • Benchmark trước khi tối ưu.
  • Test behavior và contract quan trọng hơn internal call sequence.
